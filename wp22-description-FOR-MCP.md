# ТЗ: Server Admin — админ-портал системы Compath Choir Rehearsal AI

## 1. Цель и краткое описание

**Server Admin** — единый портал администратора всей ИИ-системы Compath Choir Rehearsal AI (WP-20): ресурсы серверов, процессы и контейнеры, очереди задач, клиенты и лицензии (хоры Pro/Pro+AI и внешние API-клиенты), агент управления ресурсами с рекомендациями, мониторинг и алерты, бэкапы, восстановление и миграция, управление сторонними docker-compose стеками (первый — n8n), учёт расходов ИИ, публичный Partner/OMR API для сторонних приложений (3.18), ИИ-ассистент. Оформление — тёмная тема в стиле Zabbix. Портал — единственный UI администратора (Grafana — опционально, только для отладки). Те же данные доступны ассистенту Grok Bot через MCP-сервер.

## 2. Брендинг

* **Lockup в боковом меню:** логотип COMPATH, под ним вторая строка **SERVER ADMIN** оранжевым (#ffa059).
* В верхней панели название портала **не выводится**.
* **Favicon:** оранжевый шар с иконкой сервера; 16, 32, 180 (apple-touch), 512 px, .ico и .svg.
* **Макеты:** /workspace/admin-portal-mockup — index.html (десктоп), mobile.html (мобильная версия), PNG-скриншоты.

## 3. Функции

### 3.1 Дашборд

* Метрики серверов: CPU, RAM, диск по каждому серверу, история и графики (данные из Prometheus, см. 3.13).
* Статус серверов, текущие проблемы, статус SLO, внешнего uptime-мониторинга и последнего бэкапа (RPO); статус зарегистрированных стеков (3.16).

### 3.2 Процессы

* Контейнеры (portal, API, OMR, агент, executor, бэкап, мигратор, БД, Redis, мониторинг) и контейнеры зарегистрированных сторонних стеков (напр. n8n), сгруппированные по стеку: статус healthcheck, перезапуски, docker stats, лимиты CPU/RAM.
* Версия образа (digest), результат сканирования уязвимостей (Trivy), доступные обновления ОС/Docker/Postgres (см. 4.6).

### 3.3 Очереди

* Задачи в ожидании и в работе, время ожидания и обработки — сигнал для наращивания ресурсов.
* Алерты по симптомам (время ожидания, доля ошибок) и порогам ресурсов (мало памяти, длинная очередь) — см. 3.13.

### 3.4 Клиенты и лицензии

* Хоры, лицензии Pro / Pro+AI (из SureCart), использование (страниц OMR/мес, задачи в очереди), ошибки.
* **Внешние API-клиенты** (Partner API, 3.18): приложения и сервисы, которым продаём только распознавание/обработку на сервере Compath — без обязательного WordPress-плагина.
* Единый реестр потребителей квоты: тип (хор / partner), план, лимиты, ключи, usage, статус (active / suspended / revoked).

### 3.5 Агент управления ресурсами

* Запуск каждые **10 минут**: правила + анализ метрик (Prometheus) и логов (Loki), включая зарегистрированные стеки (напр. «n8n: ошибки выполнения workflow»).
* Ведёт список рекомендаций: описание, доказательства (графики, строки логов), набор команд.
* Также следит за бэкапами (3.11): напр. «бэкап не удался», «мало места для бэкапов», «RPO превышен».
* **Этап 2 / опционально:** прогноз ёмкости (тренды TimescaleDB) — «диск заполнится через N дней», «очередь растёт».
* **Жизненный цикл:**

    1. _Кандидат_ — агент заметил проблему (очередь, память, ошибки в логах, сбой бэкапа).
    2. _Наблюдение_ — каждая проверка повышает/понижает уверенность и приоритет; неподтвердившиеся — в «удалённые» (soft delete).
    3. _На утверждение_ — после N подтверждений рекомендация попадает в список утверждения.
    4. _Решение администратора:_ **Подтвердить** (команды выполняет compath_executor ровно в утверждённом виде, результат пишется), **Отклонить**, или **Комментарий + «протестировать снова»** (рекомендация возвращается в наблюдение).
    5. _История_ — действия агента и решения администратора в журнале.
    
* Таблица рекомендаций: счётчик подтверждений, уверенность, приоритет, статус.
* **Изоляция (см. 3.14):** агент не имеет доступа к docker.sock и секретам; сам ничего не исполняет.

### 3.6 Фильтр и поиск рекомендаций

* По умолчанию — только активные (кандидат, наблюдение, на утверждение).
* Закрытые, архив и удалённые скрыты, но доступны для поиска; физически записи не удаляются (soft delete).
* Фильтры: статус (мультивыбор, «Все»), период, сервер/ресурс/стек, приоритет.
* Поле поиска: название, описание, команды, комментарии, ID; работает с фильтрами, обновляется по мере ввода, подсветка совпадений.
* Тот же фильтр доступен через MCP.

### 3.7 ИИ-ассистент (чат)

* Выдвижная панель справа на всех страницах.
* Видит контекст страницы; через API/MCP читает метрики, логи, очереди, клиентов, рекомендации, статус бэкапов, миграции и стеков.
* Отвечает на вопросы, объясняет рекомендации и команды, ищет по журналу, может предложить рекомендацию в наблюдение.
* **Только чтение:** действия (включая восстановление и миграцию) — только через список утверждения/подтверждение.
* **Защита:** секреты (включая N8N_ENCRYPTION_KEY и credentials n8n) никогда не попадают в контекст LLM (маскирование в логах и ответах API); содержимое логов и данных — недоверенный ввод (защита от prompt injection, OWASP LLM Top 10).
* Модель: локальная LLM (напр. Ollama) или внешний API (через compath_llm_gateway) — решается в WP-21; история чата сохраняется.

### 3.8 Пользователи и роли

* **Суперадмин:** всё, что оператор, + пользователи и роли, утверждение команд, восстановление, миграция и режим оффлайн, регистрация/удаление стеков в реестре, настройки, MCP-токены, Partner API keys/квоты (3.18), ротация секретов, бюджеты/лимиты/цены ИИ.
* **Оператор:** просмотр ресурсов, процессов, очередей, клиентов, бэкапов, реестра стеков, «Расходы ИИ», журнала; чат; комментарии и «протестировать снова»; «Сделать бэкап сейчас» (вкл. стеки); «Проверить DNS». Не утверждает команды, не восстанавливает, не запускает миграцию, не переключает оффлайн/онлайн, не меняет реестр стеков и пользователей.
* Страница «Пользователи» (только суперадмин): список (имя, email, роль, статус, последний вход), фильтр и поиск, приглашение по email, смена роли, блокировка, сброс пароля/2FA.
* **2FA обязательна для всех ролей** (оператор видит ПДн и делает бэкапы); lockout после N неудачных входов; нельзя удалить последнего суперадмина; изменения прав — в аудите.
* **Этап 2 / опционально:** break-glass аккаунт (запечатанный, любое использование — критический алерт) и коды восстановления 2FA в сейфе.

### 3.9 Мобильная версия (PWA)

* Mobile-first: меню → нижняя панель/бургер, виджеты в одну колонку, таблицы → карточки, чат на весь экран.
* Главное: статус серверов и стеков, проблемы, «На утверждение» с Подтвердить/Отклонить (с повторным подтверждением), подтверждение алертов (ack).
* Виджет бэкапов: возраст последнего бэкапа/RPO (по стекам), тест-восстановление, статус immutable-копии, тревога при сбое.
* Во время миграции: прогресс в % (общий и по каждому стеку), шаг и ETA, оффлайн-режим с таймером, прогресс DNS.
* PWA: установка, push о рекомендациях, проблемах, сбоях бэкапа, прогрессе миграции (25/50/75/100%), начале/окончании оффлайна. Push дублируется внеплатформенными каналами (3.13).
* Расходы ИИ: сводка за день/месяц, алерты бюджета 80%/100%.
* Общие компоненты с мобильным приложением WP-20.

### 3.10 MCP-доступ для Grok Bot

* MCP-сервер поверх того же API: чтение метрик, очередей, клиентов, рекомендаций (с фильтром), статуса бэкапов и миграции (включая %), реестра и статуса стеков, расходов ИИ; решения по рекомендациям — по тем же правилам. Запустить миграцию, восстановление или изменить реестр стеков через MCP нельзя.
* Отдельная учётная запись с правами оператора; **токен с ограниченным scope и сроком жизни** (напр. 30 дней), плановая ротация, немедленный отзыв; все вызовы в аудите.

### 3.11 Бэкапы и восстановление

**Стратегия 3-2-1-1-0** (для стека compath и всех зарегистрированных стеков, вкл. n8n): 3 копии, 2 типа носителей, 1 off-site, **1 неизменяемая** (S3 Object Lock/WORM, compliance — не удалить даже суперадмину или злоумышленнику), **0 ошибок** при проверке восстановления.

**Цели:** **RPO ≤ 15 мин** (непрерывное WAL-архивирование Postgres + PITR через pgBackRest/WAL-G; файлы — инкрементально каждые 15 мин), **RTO ≤ 1 ч** (полное восстановление на чистую VM). Для сторонних стеков RPO/RTO задаются в реестре (по умолчанию те же). Факт показывается на странице и проверяется на DR-учениях (3.15).

**Мониторинг (страница «Бэкапы»):**

* Список: стек, дата, тип (полный дамп / WAL / файлы / конфигурация), размер, длительность, статус OK/FAIL, место хранения.
* Возраст последнего успешного бэкапа и задержка WAL с порогами: >26 ч (полный) или >15 мин (WAL) — предупреждение; сбой — критическая тревога + push + внеплатформенный канал.
* Проверка контрольных сумм; автоматическое тест-восстановление в **compath_restore_test** с результатом.
* Хранилище и политика хранения GFS (7 ежедневных, 4 еженедельных, 3 ежемесячных); статус off-site и immutable-копии (срок блокировки).
* Кнопка **«Сделать бэкап сейчас»** (для всего или выбранного стека); каждый бэкап пингует dead-man's switch (3.13).
* **Этап 2 / опционально:** снапшоты VPS на уровне провайдера как дополнительный слой.

**Состав и шифрование:**

* дамп compath_db + WAL-архив; том compath_files; docker-compose.yml, секреты (SOPS), версии/digest образов; для сторонних стеков — по адаптеру (3.16).
* **Весь бэкап шифруется** (напр. age/restic, AES-256) до отправки; ключ — отдельно от бэкапов и сервера (сейф + офлайн-копия).

**Восстановление в пару кликов (мастер):**

1. Выбор стека и точки (бэкап или момент времени — PITR).
2. Предпросмотр того, что будет восстановлено.
3. Подтверждение — только суперадмин, повторная 2FA.
4. Автоматический pre-restore snapshot.
5. Остановка сервисов, восстановление томов/БД, запуск закреплённых (digest) образов.
6. Health checks.
7. Отчёт; при неудаче — автооткат к pre-restore snapshot.

* Варианты: полная система, отдельный стек, только БД или только файлы.
* **«Восстановить на новый сервер»** — тем же пакетом, см. 3.12.
* **CLI-восстановление** (compath-restore) работает без портала по runbook (3.15).

**Агент, чат, аудит:** агент создаёт рекомендации по бэкапам; чат сообщает статус, восстановление — только через подтверждение; все действия — в неизменяемом аудите.

### 3.12 Миграция на новый сервер и переключение DNS

#### 3.12.1 Страница «Миграция» — форма целевого сервера

* Выбор объекта: стек compath, один или несколько зарегистрированных стеков вместе; **целевой VPS выбирается по каждому стеку** (3.16).
* Поля: хост/IP, SSH-порт, вход — пользователь + пароль **или** SSH-ключ/токен.
* Учётные данные — временно и зашифрованно, удаляются после миграции, **никогда не пишутся в логи**.
* Пароль используется один раз — для установки временного SSH-ключа.

#### 3.12.2 Предварительная проверка (pre-flight)

* Связность (SSH, сеть); ОС и архитектура; CPU/RAM/диск против требований (суммарно для всех выбранных стеков); Docker/compose (предлагается автоустановка); свободные порты и отсутствие конфликтов имён проектов/томов; синхронизация времени; специфичные проверки адаптера (для n8n — см. 3.16.3).
* Итог — отчёт **go / no-go** с причинами (по каждому стеку).

#### 3.12.3 Миграция в один клик

Кнопка **«Мигрировать»** (только суперадмин + 2FA):

1. Свежий пакет бэкапа (по каждому выбранному стеку).
2. Установка Docker на целевом сервере (если нужно).
3. Зашифрованная передача с контрольной суммой.
4. Развёртывание закреплённого compose + секретов (имена сторонних стеков сохраняются).
5. Восстановление БД и файлов, применение миграций схемы (4.5); для сторонних стеков — шаги адаптера.
6. Health checks (вкл. проверки адаптера).
7. Далее — шаги оффлайн/DNS (3.12.5).

#### 3.12.4 Прогресс, отмена, история

* Общая шкала 0–100%, взвешенная по шагам и стекам; % по шагу (передача — по байтам со скоростью и ETA, восстановление БД — по размеру).
* Текущий шаг, прошедшее время и ETA; десктоп и мобильная версия; push при 25/50/75/100%; статус читается через MCP.
* Кнопка **«Прервать»**; при сбое или отмене старый сервер остаётся активным.
* История миграций (дата, стеки, цель, результат, длительность, кто запускал).
* Агент может рекомендовать миграцию только через список утверждения; MCP не может её запустить.

#### 3.12.5 Переключение DNS и оффлайн-режим

**Подготовка:** напоминание заранее снизить TTL (рекомендуется 300 с).

1. Перенос и восстановление на новом сервере (3.12.3).
2. Health checks 100% → система предлагает оффлайн-режим, т.к. нужна смена DNS.
3. **«Перейти в режим оффлайн?»** — подтверждение суперадмином.
4. Старый сервер показывает страницу техобслуживания; приём задач приостановлен; задачи в работе завершаются или сохраняются; для n8n — пауза активных workflow/триггеров (3.16.3).
5. Финальный delta sync.
6. Портал показывает точные DNS-записи: тип (A/AAAA/CNAME), имя, старый → новый IP, рекомендуемый TTL (по каждому домену/стеку).
7. **«Проверить DNS»** — распространение через несколько публичных резолверов, % и статус по каждому.
8. Когда домен резолвится на новый сервер — health check через домен и выпуск TLS-сертификата; для n8n — перерегистрация внешних webhook.
9. **«Вернуть онлайн»** — сервис работает на новом сервере (workflow n8n реактивируются).
10. Старый сервер — read-only резерв (fallback).

* **Откат:** вернуть DNS (и webhook-регистрации) и выйти из обслуживания на старом сервере.
* Таймер длительности оффлайна; push и внеплатформенные уведомления о начале/окончании; все шаги в аудите.

#### 3.12.6 Этап 2 / опционально

* Миграция с минимальным простоем: логическая репликация Postgres (новый сервер догоняет в реальном времени, переключение за секунды) вместо оффлайн + delta sync; или blue-green через reverse proxy.
* Floating IP провайдера или reverse proxy (Cloudflare) — переключение без ожидания DNS.

### 3.13 Мониторинг, алерты и логи

* **Метрики:** Prometheus + node_exporter + cAdvisor + postgres_exporter вместо самописного сбора (вкл. контейнеры сторонних стеков и их БД); часовые агрегаты — в TimescaleDB.
* **Логи:** централизованно в Loki (сбор через Promtail/Alloy), ретеншен 30 дней — логи переживают падение контейнера, агент читает их отсюда.
* **Алерты по SLO/симптомам** (доступность API, время обработки задач, доля ошибок; для n8n — healthz и доля ошибочных выполнений), а не только по ресурсам; Alertmanager — маршрутизация.
* **Внешний мониторинг:** uptime-чек портала/API (и публичных точек сторонних стеков, напр. n8n webhook) с другой площадки (UptimeRobot/Uptime Kuma на внешнем хосте) + **dead-man's switch** (Healthchecks.io: heartbeat от Alertmanager Watchdog и от каждого бэкапа) — алерт придёт, даже если сервер упал целиком.
* **Каналы вне сервера:** email, Telegram, SMS (не только PWA push). **Эскалация:** критический алерт → push + Telegram сразу; без подтверждения (ack) 15 мин → SMS/звонок; email — всегда.
* Каждый алерт ссылается на свой runbook (3.15).
* **Этап 2 / опционально:** публичная status page для клиентов на внешнем хостинге.

### 3.14 Безопасность платформы

* **Доступ к порталу:** не публикуется в интернет — WireGuard/VPN или IP allowlist; reverse proxy с TLS; rate limiting и lockout логина; защищённые сессии (HttpOnly, Secure, SameSite, тайм-аут), CSRF-токены; security headers (CSP, HSTS, X-Frame-Options); соответствие OWASP ASVS.
* **Секреты:** не хранятся открыто в .env — Docker secrets + SOPS (в git только зашифрованные); плановая ротация паролей БД, API-ключей и MCP-токенов. Секреты сторонних стеков (вкл. N8N_ENCRYPTION_KEY) хранятся так же.
* **Изоляция агента:** compath_agent и чат без docker.sock и секретов; утверждённые команды выполняет отдельный **compath_executor** с минимальными правами через **compath_socket_proxy** (только разрешённые вызовы Docker API) и белый список команд.
* **Цепочка поставки:** образы закреплены по digest; сканирование уязвимостей Trivy в CI и на сервере (критические — блокируют деплой и создают рекомендацию).
* **Аудит:** append-only (без UPDATE/DELETE, хеш-цепочка), ежедневная копия в immutable off-site хранилище — суперадмин не может стереть следы.

### 3.15 Runbooks и DR-учения

* **Runbooks** для каждого алерта и DR-сценария (сервер умер полностью, БД повреждена, ransomware, компрометация аккаунта, восстановление n8n) — хранятся вне сервера (git + офлайн-копия).
* Восстановление и миграция работают и **из CLI без портала**.
* **DR-учения раз в квартал:** полный restore (вкл. сторонние стеки) на чистую VM с замером фактического RTO/RPO, отчёт и улучшения в runbook.

### 3.16 Управление стеками и перенос сторонних сервисов (n8n)

**Цель:** управлять не только стеком compath, но и любыми docker-compose стеками на сервере теми же механизмами. Первый — **n8n** на VM 10.10.10.23 (n8n + его Postgres + Redis), в котором сейчас создаётся workflow бота поддержки участников хора; всё это позже переезжает на VPS.

#### 3.16.1 Реестр стеков (страница «Стеки»)

* **Регистрация стека:** имя, путь к docker-compose.yml, тома данных, .env/секреты, тип БД (Postgres/MySQL/SQLite/нет), домены, адаптер (generic или специфичный, напр. n8n), целевые RPO/RTO, целевой сервер.
* **Автообнаружение** запущенных compose-проектов (по меткам com.docker.compose.project, только чтение через compath_socket_proxy) с предложением зарегистрировать.
* **По каждому стеку** — те же механизмы: мониторинг и алерты, бэкапы (3-2-1-1-0), восстановление, миграция (pre-flight, % прогресса, оффлайн/DNS, откат), аудит.
* **Имена не меняются:** сторонние стеки сохраняют свои имена контейнеров, томов и сетей (не compath\_\*); стек compath их не трогает и не переименовывает; в реестре хранятся только метаданные.
* Изменения в стороннем стеке (рестарт, обновление) — только через список утверждения и compath_executor.

#### 3.16.2 Миграция стеков

* Можно перенести один стек или несколько вместе (напр. compath + n8n) в одном запуске; целевой VPS выбирается по каждому стеку.
* Порядок и зависимости между стеками учитываются; оффлайн и DNS-переключение — по каждому домену; откат — по каждому стеку отдельно.

#### 3.16.3 Адаптер n8n

* **N8N_ENCRYPTION_KEY сохраняется без изменений** (иначе credentials нечитаемы); хранится как секрет (SOPS), входит в зашифрованный бэкап; pre-flight проверяет его наличие и совпадение.
* **Данные:** БД Postgres n8n (дамп + WAL), том данных n8n (/home/node/.n8n), Redis — если используется queue mode (перед переносом очередь дорабатывается).
* **Версия:** образ n8n закреплён по digest; на целевом сервере та же версия; обновление n8n — отдельно, после миграции (4.6).
* **Перед оффлайном:** пауза активных workflow/триггеров (список активных сохраняется), ожидание завершения текущих выполнений.
* **После смены домена/IP:** обновление WEBHOOK_URL, N8N_HOST, N8N_PROTOCOL (и N8N_EDITOR_BASE_URL); перерегистрация внешних webhook (Telegram bot setWebhook и др.) — автоматически при реактивации триггера или по чек-листу в реестре для внешних сервисов; статус каждой регистрации показывается.
* **После переноса:** реактивация ранее активных workflow; проверка через **/healthz** n8n и **тестовое выполнение ключевых workflow** (вкл. бот поддержки участников хора — тестовое сообщение и ответ); список ключевых workflow задаётся в реестре.
* **Дополнительный бэкап (опционально):** экспорт workflow и credentials через n8n CLI (export:workflow / export:credentials, credentials — в зашифрованном виде), входит в тот же зашифрованный пакет.
* Бэкапы стека n8n включены в политику 3-2-1-1-0 (3.11), с тест-восстановлением и алертами.

### 3.17 Расходы ИИ / учёт токенов

* **Единый LLM-шлюз compath_llm_gateway** (напр. LiteLLM proxy): через него идут **все платные LLM-вызовы** (OpenAI, Anthropic и др.) — агенты compath, ИИ-чат, будущие ИИ-функции OMR/WP-23, workflow n8n. Каждому вызывающему — свой виртуальный ключ; ключи провайдеров — только в секретах шлюза (Docker secrets/SOPS).
* **Журнал вызовов:** вызывающий (агент / workflow+узел n8n / хор-клиент / пользователь), провайдер, модель, input/output токены, стоимость (по обновляемой таблице цен), задержка, статус. Хранение — Postgres/TimescaleDB.
* **n8n:** LLM-узлы направляются в шлюз (OpenAI-совместимый base URL + виртуальный ключ workflow); резерв — сбор usage токенов из данных выполнений n8n.
* Audiveris (OMR) платных токенов не использует.
* **Страница «Расходы ИИ»:** графики по дням/месяцам, разбивка по агенту/workflow/клиенту/модели, топ потребителей, экспорт CSV.
* **Бюджеты и лимиты** на агента/клиента: алерты при 80% и 100% (push + внешние каналы), опционально жёсткая остановка (шлюз отклоняет вызовы).
* **Pro+AI (WP-23):** месячные лимиты клиента и докупаемые пакеты применяются на шлюзе.
* Доступ: оператор — просмотр; суперадмин — бюджеты, лимиты, цены, ключи; MCP и мобильная версия — чтение.


### 3.18 Публичный Partner / OMR API для сторонних сервисов и приложений

**Цель:** продавать распознавание нот и связанные ИИ-операции как отдельную услугу. Любое стороннее приложение (не только плагин Choir Rehearsal и не только мобильный клиент Compath) может вызывать сервер Compath по HTTP API: загрузить файл → получить MusicXML/JSON. Плагин WordPress и будущие клиенты Compath — первые потребители того же API; внешние разработчики — платящие партнёры.

Связано: WP-19 (OMR), WP-20 (единый движок/API), WP-23 (тарифы и квоты Pro+AI / API), WP-25 (прогоны + Layer D grammar).

#### 3.18.0 Преимущества продукта (для shop / Partner page / Pro+AI)

1. **OMR → MusicXML** — PDF/скан → `.mxl` / MusicXML (MuseScore, веб-плееры).
2. **Нотная грамота на лету** — hard/soft правила тональности поверх Audiveris (напр. си♭ в ключе ↛ си♯; g-moll → F♯ вводный).
3. **Память правок (Redis)** — выученные коррекции ускоряют повторные прогоны; не перебивают hard-правила.
4. **Многослойный QA** — structural / visual / piano-roll / tonal + `confidence` (best-effort).
5. **0 LLM-токенов на грамматику** — CPU-only; LLM опционально через шлюз.
6. **Тот же licensing, что Pro** — SureCart → license → activation → API keys.
7. **Partner без обязательного WP**; плагин хора offline-capable для базовой библиотеки.

Публичный бесплатный «учебник гармонии JSON API» — **не** продукт. Grammar — лицензированный слой OMR / будущий `/v1/grammar/check` в квоте подписки.

#### 3.18.1 Продуктовая модель

* **Два канала доступа к одному ядру** (`compath_api` + `compath_omr_worker`):
  1. **Choir clients** — лицензия Pro / Pro+AI (SureCart), сайт хора / будущий mobile.
  2. **Partner API** — API-ключ организации, биллинг по квоте (страницы / jobs / MB), без обязательного WP.
* Плагин остаётся работоспособен **без** облака для базовой библиотеки (треки, PDF, sticky player). OMR и прочие тяжёлые ИИ-функции — opt-in через облако.
* Партнёр **не получает** доступ к Server Admin, MCP, секретам, реестру стеков и данным других клиентов.

#### 3.18.2 Возможности API (v1 → v1.x)

**MUST (v1) — OMR:**

* `POST /v1/omr/jobs` — создать задачу (multipart: PDF/PNG/JPEG; опции: язык/ожидаемые партии, webhook URL, idempotency-key; `grammar_pass=true` по умолчанию).
* `GET /v1/omr/jobs/{id}` — статус (`queued` / `running` / `succeeded` / `failed` / `cancelled`), прогресс %, ошибки.
* `GET /v1/omr/jobs/{id}/result` — артефакты: MusicXML (`.musicxml` / `.mxl`), JSON (страницы, партии, confidence, **grammar corrections** / disputes), опционально превью.
* Worker: Audiveris → Layer D+ tonal grammar → Redis memory hints → export.
* `DELETE /v1/omr/jobs/{id}` — отмена в очереди / запрос на удаление артефактов.
* `GET /v1/usage` — остаток квоты, usage за период.
* Асинхронная модель обязательна (OMR долгий): poll и/или **webhook** (HMAC-подпись тела, повторные доставки с backoff).

**SHOULD (v1.x) — смежные операции того же биллинга:**

* Разбор уже готового MusicXML (normalize / split voices) без OMR.
* `POST /v1/grammar/check` — проверка/правка MusicXML правилами грамоты без полного OMR.
* Сравнение пения/аудио с эталонным треком или нотами (движок WP-20) — отдельные job-типы в той же очереди.
* Пакетная загрузка (несколько файлов / ZIP) с общим лимитом.

**COULD (этап 2):**

* Синхронный «быстрый» путь только для мелких одностраничных файлов (с жёстким timeout).
* On-prem / private endpoint для издателей и школ (отдельный договор).

#### 3.18.3 Контракт, версии, качество

* Версия в пути (`/v1/...`); breaking changes — только `/v2` с периодом deprecation.
* OpenAPI 3 спецификация публикуется и версионируется вместе с API; примеры curl/SDK (минимум: HTTP + один официальный клиент, напр. TS или Python).
* OMR — **best-effort**: в ответе обязательны `confidence` / предупреждения по страницам и партиям; SLA формулируется как доступность API и время в очереди, **не** как «идеальная партитура».
* Рукописные и плохие сканы могут давать ошибки — это ожидаемо (WP-19); партнёр обязан иметь UX проверки/правки у себя.

#### 3.18.4 Аутентификация, квоты, биллинг

* Auth: `Authorization: Bearer <api_key>` (или `X-Api-Key`); ключи привязаны к **организации** (partner account).
* Ключи: создание, ротация, отзыв, несколько ключей на org (prod/test); test-ключ с урезанной квотой и watermark/`test: true` в метаданных.
* Квоты: страницы/мес и/или jobs/мес + hard cap одновременных задач; 429 при превышении с `Retry-After`.
* Биллинг: пакеты (credits) и/или подписка; usage пишется в тот же учёт, что и клиенты хоров (3.4); перерасход — блок или overage (настройка суперадмина).
* Pro+AI (WP-23) может включать N OMR-страниц/мес для хора; Partner API — отдельный прайс (страница «Клиенты» и будущий developer portal).
* Audiveris/OMR **не** идёт через `compath_llm_gateway` (токены не тратит); учёт — **jobs/pages**, не LLM-токены. Если позже появится LLM-постобработка нот — только через шлюз (3.17) и отдельная строка расходов.

#### 3.18.5 Изоляция, безопасность, GDPR

* Tenant isolation: файлы и результаты одного partner/хора недоступны другому; пути в `compath_files` с префиксом tenant.
* Retention по умолчанию: исходники и артефакты удаляются через **N часов** после `succeeded`/`failed` (настраиваемо, по умолчанию ≤ 72 ч); partner может запросить earlier delete.
* Rate limiting на IP и на ключ; max размер файла и max страниц на job; антивирус/проверка типа файла.
* Партнёр подтверждает права на загружаемые партитуры (ToS); Compath не становится издателем и не публикует чужие ноты.
* **Авторское право:** документы D1–D7 и шаги 20i–20p — §3.18.9 полного ТЗ; memo `2026-10-12-omr-copyright-rights-memo.md` (AutÕS/DSM).
* ПДн: Partner API по возможности **без** ПДн участников хора; если в метаданных передают email/user id — те же GDPR-правила, что в 4.3/5.
* Публичный API endpoint — за reverse proxy с TLS; **отдельная** поверхность от VPN-only Server Admin (3.14). Admin-портал в интернет не публикуется; Partner API — да (с WAF/rate limit).
* Аудит: создание/отзыв ключей, превышение квот, массовые ошибки — в неизменяемый журнал; MCP/чат видят агрегаты, не сырые файлы партнёров без необходимости.

#### 3.18.6 Очереди, приоритеты, наблюдаемость

* Общая очередь OMR (Redis) с **приоритетами**: Pro+AI хоры / SLA-партнёры vs free-tier/test.
* Метрики: длина очереди, wait time p50/p95, error rate, pages/min — на дашборде (3.1/3.3) и в алертах SLO (3.13).
* Агент (3.5) может рекомендовать scale-out `compath_omr_worker` при росте очереди Partner+Choir.
* Страница «Клиенты»: фильтр choir vs partner, usage, ошибки job’ов, статус ключей.
* Суперадмин: suspend org, revoke all keys, изменить квоту, принудительно purge файлов.

#### 3.18.7 Developer experience (вне портала оператора)

* Публичная документация (OpenAPI + гайд): auth, job lifecycle, webhooks, коды ошибок, лимиты.
* Sandbox/test keys без прод-биллинга (или с микро-квотой).
* Статус инцидентов — через внешнюю status page (этап 2, 3.13) или статус-эндпоинт.
* **Не** смешивать ключи SureCart/лицензии плагина и Partner API keys без явной связки продуктов в биллинге.

#### 3.18.8 UI в Server Admin

* Раздел **«API / Partners»** (или вкладка в «Клиенты»): список org, план, квота, usage, ключи (только префикс + last4, полный секрет — один раз при создании), журнал job’ов.
* Действия суперадмина: создать org, выпустить ключ, ротация, revoke, suspend, изменить квоту, purge.
* Оператор: просмотр usage/ошибок; выпуск ключей — только суперадмин (или по отдельному праву на этапе 2).
* Мобильная версия: сводка usage и алерты 80%/100% квоты партнёров.
* MCP: чтение агрегатов usage/очереди Partner API; создание ключей и purge через MCP — **запрещены**.

## 4. Архитектура и хранение

### 4.1 Контейнеры и docker-compose

* Каждый компонент — в своём контейнере; весь стек — один переносимый docker-compose со своими томами и секретами, **без зависимостей от n8n и хоста**.
* **Для каждого сервиса обязательно:** healthcheck, restart: unless-stopped, лимиты CPU/RAM, ротация логов (json-file, max-size/max-file), образ по digest, порядок запуска через depends_on: condition.
* Перенос: compose + тома (или бэкап) и `docker compose up`, либо страница «Миграция» (3.12).
* Все имена с префиксом **compath\_**; проект compose — **compath**.
* **Сторонние стеки** (напр. n8n + его Postgres + Redis на 10.10.10.23) — отдельные compose-проекты со своими именами, не переименовываются; обслуживаются через адаптеры (3.16).

| Контейнер | Назначение |
| --- | --- |
| compath_portal | веб-портал и PWA, страница техобслуживания |
| compath_api | общее ядро/API (admin + публичный Partner/OMR), MCP-сервер, реестр стеков |
| compath_omr_worker | распознавание нот (Audiveris), образ **compath_omr** (переименовать из compath-omr) |
| compath_agent | агент управления ресурсами (без docker.sock и секретов) |
| compath_executor | исполнение только утверждённых команд из белого списка |
| compath_socket_proxy | docker socket-proxy с минимумом разрешённых вызовов |
| compath_backup | бэкапы всех стеков (адаптеры), WAL/PITR, шифрование, тест-восстановление (compath_restore_test), off-site/immutable, delta sync |
| compath_migrator | оркестратор миграции стеков (3.12, 3.16) и миграций схемы БД |
| compath_llm_gateway | LLM-шлюз (LiteLLM proxy): платные LLM-вызовы, виртуальные ключи, учёт токенов/стоимости, лимиты (3.17) |
| compath_db | PostgreSQL + TimescaleDB |
| compath_redis | очередь и живые статусы |
| compath_prometheus | метрики + exporters (compath_node_exporter, compath_cadvisor, compath_postgres_exporter) |
| compath_alertmanager | маршрутизация алертов, эскалация, Watchdog |
| compath_loki | централизованные логи (+ compath_promtail для сбора) |
| compath_grafana | опционально, для отладки; основной UI — портал |

* Тома: **compath_db_data**, **compath_files**, **compath_prometheus_data**, **compath_loki_data**; сеть: **compath_net**.

### 4.2 Контейнер и том — в чём разница

* **compath_db** — контейнер, т.е. программа PostgreSQL; его можно удалить, заменить или обновить.
* **compath_db_data** — том с файлами базы; переживает замену/обновление контейнера.
* Для переноса копируется том (или его бэкап), контейнер создаётся заново из образа. То же самое для сторонних стеков (тома n8n и его Postgres).

### 4.3 Данные

* **PostgreSQL + TimescaleDB:** пользователи и роли, клиенты и лицензии, история очереди, рекомендации и комментарии, аудит (append-only), история бэкапов и миграций, реестр стеков (только метаданные, без секретов), журнал LLM-вызовов и расходов ИИ, метрики (детальные 30 дней, почасовые 1 год).
* **Redis:** очередь и живые статусы (включая прогресс миграции).
* **Prometheus / Loki:** метрики и логи, ретеншен 30 дней.
* **Файлы** (PDF/JPG, MusicXML, аудио): том compath_files, позже S3-совместимое хранилище; префикс tenant (хор / partner); для Partner API — короткий retention по умолчанию (3.18.5).
* **Бэкап:** WAL непрерывно (RPO ≤ 15 мин), полный дамп ночью, файлы инкрементально; шифрование; off-site immutable (3.11) — для compath и зарегистрированных стеков.
* **ПДн:** сроки хранения определены; удаление по запросу (GDPR ст.17) — из БД сразу, из бэкапов — по истечении ретеншена GFS (≤ 3 мес), журнал удалений повторно применяется после любого восстановления. ПДн участников хора в n8n (бот поддержки) подпадают под те же правила.

### 4.4 Размещение

* Собственный сервер: сейчас тестовая VM 10.10.10.23 (далее — staging; там же стек n8n), позже VPS в ЕС (стеки могут размещаться на одном или разных VPS); off-site хранилище тоже в ЕС, DPA с провайдерами.
* Ресурсы наращиваются по мере нагрузки (данные очередей и рекомендации агента).
* Логика — в общем ядре/API, не в WordPress, чтобы её использовали плагин, мобильное приложение и **внешние Partner API-клиенты** (3.18).
* **Публичный Partner API** и **VPN-only Server Admin** — разные входные поверхности одного `compath_api` (разные virtual host / routes, разные auth: API-key vs сессия оператора); админка в интернет не публикуется.

### 4.5 Миграции схемы БД

* Версионированные, **forward-only** (откат — новой миграцией или восстановлением).
* Выполняет compath_migrator как одноразовый шаг до старта compath_api (depends_on: service_completed_successfully).
* **Перед каждой миграцией схемы — автоматический бэкап**; при ошибке — остановка и откат к бэкапу.
* Схему БД сторонних стеков (n8n) мигрирует само приложение при обновлении версии — только после бэкапа и проверки на staging.

### 4.6 Обновления и патчи

* Ежемесячное окно обслуживания (критические CVE из CISA KEV — сразу) для ОС, Docker, Postgres/Timescale, образов (вкл. n8n).
* Порядок: бэкап → обновление на staging → проверки → прод; всё через список утверждения и аудит.

## 5. Нефункциональные требования

* **Надёжность:** RPO ≤ 15 мин, RTO ≤ 1 ч, SLO доступности API (напр. 99,5%) — проверяются на DR-учениях.
* **Безопасность (3.14):** роли, 2FA для всех, VPN/allowlist, rate limiting/lockout, CSRF, headers, секреты в Docker secrets/SOPS с ротацией, scoped MCP-токены, неизменяемый аудит с off-site копией.
* **Без автовыполнения:** только утверждённые команды, ровно в утверждённом виде, через compath_executor (белый список, лог, откат). LLM и агент не видят секретов.
* **Бэкапы и восстановление (3.11):** 3-2-1-1-0 для всех стеков, шифрование с отдельным ключом, immutable off-site, контрольные суммы, тест-восстановление, GFS; restore — суперадмин + 2FA, pre-restore snapshot, автооткат, CLI.
* **Миграция (3.12):** учётные данные временно и зашифрованно, не логируются; передача с контрольной суммой; суперадмин + 2FA; при сбое старый сервер активен; минимальный оффлайн без потери задач; откат через DNS.
* **Сторонние стеки (3.16):** не изменяются и не переименовываются; n8n — сохранение N8N_ENCRYPTION_KEY и тест ключевых workflow после restore/миграции.
* **Расходы ИИ (3.17):** ни одного платного LLM-вызова в обход шлюза; бюджеты и лимиты применяются на шлюзе.
* **Partner / OMR API (3.18):** публичный TLS-endpoint отдельно от VPN-admin; tenant isolation; квоты и 429; короткий retention файлов; ключи с ротацией/отзывом; OMR best-effort (confidence в ответе); партнёр не видит данные других клиентов и не получает прав администратора.
* **Наблюдаемость:** внешний мониторинг, dead-man's switch, алерты вне сервера с эскалацией, runbook на каждый алерт.
* **GDPR:** реестр обработки (ст.30), DPA (ст.28), хранение в ЕС, шифрование (ст.32), сроки хранения и удаление вкл. бэкапы, уведомление об утечке за 72 ч (ст.33).
* Переносимость, мягкое удаление, тёмная тема, адаптивность.
